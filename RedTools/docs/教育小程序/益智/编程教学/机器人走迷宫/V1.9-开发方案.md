## 1. 背景与目标

### 1.1 背景

走迷宫已完成编程核心概念八块闭环：顺序（v1.0）→ 循环（v1.1）→ 条件（v1.3）→ 调试（v1.4）→ 分支（v1.5）→ 参数化（v1.6）→ 循环块（v1.7）→ 嵌套循环（v1.8）。
八块概念教学全部走「内置关卡 → 孩子解题」单向路径。v1.9 补足**创作闭环**：孩子**自己设计关卡**（放箱/目标/墙，让机器人/同学来解）——编程教学最高阶能力（抽象问题 → 表达为可执行盘面）。

### 1.2 教学定位

- 1-8 块：**解题**（给定盘面 → 写指令）
- **v1.9：** **出题**（设计盘面 → 校验可解 → 保存/挑战/分享）——角色反转，逆向理解推箱子判定
- 教学价值：设计关卡时孩子必须理解「箱子能否被推到目标」「路径是否可行」——比解题更深的盘面结构理解
- 类比：编程课「改题/出题」环节；数学「自己出应用题」

### 1.3 与既有能力关系

| 能力 | 现状 | v1.9 |
|---|---|---|
| 关卡数据 | levels.js 只读数组（205 关，b=最优步数） | 新增**自定义关卡库**（localStorage 持久化） |
| 进关流程 | startGame('easy/normal/hard') → levelIdx 映射 | 新增 startCustom(idx) → 自定义关卡进入同一练习/判定/星级流程 |
| 星级 | b=null 兜底 2★（19 关先例） | 自定义关卡 b=null → 兜底 2★（无最优步数基准） |
| 盘面判定 | parseLevel(XSB) + isWon | 复用（编辑器产出 XSB 格式 g 数组） |

### 1.4 目标

| 项 | 说明 |
|---|---|
| 教学目标 | **关卡创作**：设计盘面（墙/箱/目标/玩家）→ 校验可解 → 保存到关卡库 → 从首页进入自建关挑战 |
| 玩法 | 首页新增「🛠 自建关卡」入口 → 编辑器（网格绘制）→ 校验 → 保存；关卡库列表 → 进入练习 |
| 合规 | 自建关卡**本地存储、不入 publish**（仅孩子本机可玩）；可解性校验 = **防死关挫败（UX 保障）**，非合规硬要求（N1 修订：custom 不对外分发，无"有标准答案"合规义务） |
| 合规红线 | 不引入 PK/排行榜/云存档；自建关卡本地存储（LX_SHARED.storage） |

## 2. 变更设计

### 2.1 数据模型：自定义关卡库

**存储**：`LX_SHARED.storage`（B5 复核修订：main.js L26 实际 `toolName: 'jiqirenzoumi'`（无"gong"，= 机器人走迷 拼音）；storage.js `prefix(key)` = `'redtools.' + toolName + '.' + key`——**'v1' 是 store 的 key 参数而非固定前缀段**）：
```js
// storage.set('customLevels', arr) → 实际 localStorage 键 = 'redtools.jiqirenzoumi.customLevels'（无 .v1. 段）
// value: [{ id, name, g: [...XSB rows], createdAt, solved }, ...]
```
> ⚠️ **勿硬编码完整键名**（含"gong"的错误键会绕过 storage 前缀约定、且不被"清除所有数据"清理）。统一用 `LX_SHARED.storage.set('customLevels', arr)` / `get('customLevels')`（API 自动生成正确键）。

| 字段 | 说明 |
|---|---|
| id | 唯一（N4 修订：`Date.now() + '-' + Math.random().toString(36).slice(2,5)`，防毫秒级碰撞） |
| name | 关卡名（默认「我的关卡 N」，≤12 字） |
| g | XSB 行数组（同 levels.js 格式：`#`墙/`@`玩家/`$`箱/`.`目标/空格；`*`=箱在目标，`+`=玩家在目标） |
| createdAt | 创建时间戳 |
| solved | 是否已用指令通关过（记录「已解」徽章） |

**上限**：最多 20 关（超限提示删除旧关）；每关盘面 ≤ 12×12（编辑网格 12×12 固定）。
**保存裁剪**（N2 采纳）：保存时 auto-trim 全空行/全空列（孩子只在局部涂时，不浪费存储、盘面不显大片空白）。

**存取函数**（I2 修订，明确签名）：
| 函数 | 签名 | 说明 |
|---|---|---|
| loadCustomLevels | `() → Array` | IIFE 顶部 `var customLevels = loadCustomLevels()`（与 store 同加载时机）；无数据返回 `[]` |
| saveCustomLevels | `(arr) → void` | `storage.set('customLevels', arr)` |
| addCustomLevel | `(g, name) → id` | 校验后调用；构造对象 push + save；超 20 提示 |
| removeCustomLevel | `(id) → void` | confirm 后按 id 过滤 + save |
| markCustomSolved | `(idx) → void` | `customLevels[idx].solved = true; saveCustomLevels(customLevels)` |

### 2.3 编辑器视图（viewEditor）

**布局**（仿 editCtx 风格，独立视图）：
```
┌──────────────────────────────────┐
│ [‹ 返回] 🛠 关卡编辑器 ⏱ 12×12     │
│ 名称: [________]（≤12字）          │
│ ┌────────────────────────────┐ │
│ │  12×12 网格（可绘制）         │ │  ← 中央网格
│ └────────────────────────────┘ │
│ 工具: [🧱墙] [📦箱] [🎯目标] [🤖玩家] [🧹橡皮] │
│ 校验: [✓ 检查可解]  [💾 保存]  [↺ 清空]  │
└──────────────────────────────────┘
```

**绘制交互**（I1 修订：**分层涂格模型**）：
- 每格独立维护 `{wall, goal, box, player}` 四布尔层（编辑态 `editCells[y*w+x]`）
- 工具按钮选当前画笔（墙/箱/目标/玩家/橡皮）；指针事件 `pointerdown` + `pointermove` + `setPointerCapture`（Chrome 55+ 支持，Chrome 61 基线内）
- **分层语义**（低龄直观）：
  - 涂「墙」：清空该格所有层 → wall=true（墙排他）
  - 涂「目标」：goal=true（不碰 box/player）
  - 涂「箱」：box=true（不碰 goal/player）
  - 涂「玩家」：清旧玩家格 → 当前格 player=true（唯一）
  - 涂「橡皮」：清空该格所有层
- 序列化 XSB（保存时）：wall→`#`；box+goal→`*`；box→`$`；goal+player→`+`；goal→`.`；player→`@`；空→` `

**校验（✓ 检查可解）**：
| 检查项 | 规则 |
|---|---|
| 玩家 | 恰 1 个（0/2+ → 「请放 1 个机器人」） |
| 箱子 | ≥1（「请至少放 1 个箱子」） |
| 目标 | ≥1（「请至少放 1 个目标」） |
| 箱/目标重叠 | 允许（XSB `*`；渲染 goals+boxes 叠加已支持） |
| **可解性** | **`isLevelSolvable(g)`（从零实现 BFS，B1/B2 修订）** |
| 墙闭合 | 不强制（边界即墙：parseLevel 越界即障碍，安全） |

**`isLevelSolvable(g)` 设计**（B1 修订：**非"复用"——全仓库无 JS 求解器，`b` 值由推箱子 convert_levels.py 构建期 Python 计算**；B2 修订：**push-state BFS + 死锁剪枝 + 上限 20 万**）：
- 状态 = `(归一化玩家区域, 排序后箱子位置集)`——玩家可达区用 flood fill 归一化（非每格计状态）
- 转移 = 每个箱子 × 4 方向推动（玩家可达箱子旁 + 落点合法非墙/非箱）
- **死锁剪枝**（关键，覆盖 80%+ 死锁）：
  - **角死锁**：箱子在两墙夹角且该格非目标 → 该状态不可达目标，剪枝
  - **边死锁**：箱子贴墙且沿墙方向无目标 → 剪枝
- 目标判定：所有箱子在目标位
- 状态去重：字符串哈希 `player@sorted_boxes.join(',')`
- **状态上限 20 万**（1-2 箱常规 <5k 状态；3 箱简单关 <10 万，留余量）；超限返回「暂不确定」（比假阴性友好，提示缩小关卡）
- **编辑器箱数上限降为 3**（B2 修订：4 箱状态空间百万级，50k/20 万均不可靠）
- 预估 250-300 行（含死锁剪枝；非 v0.1 声称的"200 行内"）

**保存**：
- 校验通过才可保存（「✓ 可解！保存成功」）；未校验/不可解 → 提示先检查
- 保存 → 写入 customLevels 数组 → 返回关卡库列表（新关出现在列表）

### 2.4 自定义关卡练习（startCustom）

**进入**：关卡库列表点 [▶ 挑战] → `startCustom(idx)`（I3 修订：复刻 startGame 完整启动序列）：
```js
function startCustom(idx) {
  state.firstFail = null; state.absStep = 0; state.execLock = false;  // ① 复位调试状态
  if (editStack.length) { closeEditCtx(); }                            // ② 关编辑区
  state.level = 'custom'; state.levelIdx = -1; state.customIdx = idx; // ③ 双态标记
  state.cmds = []; state.finished = false;                            // ④ 清指令
  loadLevelState(); renderGame();                                      // ⑤ 载盘+渲染
  state.startMs = Date.now(); startTimer();                           // ⑥ 计时
}
```

### 2.6 合规与数据边界

- 自建关卡**本地存储**（`LX_SHARED.storage` 键 `customLevels` → localStorage `redtools.jiqirenzoumi.v1.customLevels`），不联网、无云同步（符合离线 zip 约束）
- 自建关卡**不入 publish**（仅孩子本机可玩，非对外分发内容）——因此可解性校验是 **UX 保障（防死关挫败）**，非合规硬要求（N1）
- **「清除所有数据」覆盖**（B5）：viewParent 的清除操作除 `storage.remove('v1')` 外，**追加 `storage.remove('customLevels')`**，确保自建关卡随数据清除一并删除
- 编辑器无排行/无分享传播（合规红线）

### 4.2 可解性 BFS 自检（Node 独立脚本）

- isLevelSolvable 逻辑用 Node 跑（与前端同一实现源）
- **必须构造样例**（I4 补充，覆盖死锁类型）：
  1. 空盘面（无玩家/箱/目标）→ 校验拦截提示
  2. 全墙盘面 → 拦截
  3. 无玩家 → 拦截
  4. 单箱单目标相邻 → 可解 ✅
  5. 箱贴角墙（两墙夹角非目标）→ **不可解**（角死锁剪枝生效）
  6. **箱贴边墙且沿墙方向无目标** → 不可解（边死锁剪枝生效）
  7. **双箱走廊互锁**（两箱相邻走廊，推一个必推另一入墙）→ 不可解
  8. **部分解死锁**（一箱已到位但另一箱被堵死）→ 不可解
  9. **3 箱 × 12×12 可解关** → 可解且状态数 <20 万（验证上限不假阴性）
  10. 随机 100 个盘面（含可解/不可解混合）→ 判定无矛盾（可解的 BFS 必找到解；不可解的快速剪枝不误判）
