## 1. 定位与威胁模型

### 1.1 背景（决策点4 演进）

| 阶段 | 方案 | 状态 |
|---|---|---|
| 一 | `config.json` 明文 `api_base`（可改，换服务器只改一个字段） | ✅ `d0506fe` |
| 二 | **服务端签名配置 + 本地加密缓存**（防篡改升级） | ✅ `df0bc16` |

用户关键洞察：**这些工具/内容包「数据来自服务器更新的插件、内容清单」——服务器地址是唯一需事先明确的配置**。但明文 `config.json` 可被任何人改写指向恶意服务器。二阶段引入「平台私有配置不可伪造」：配置内容受 ed25519 签名保护，`api_base` 仅作引导入口。

### 1.2 威胁分层与对策

| 威胁 | 场景 | 对策层 |
|---|---|---|
| 本地篡改 | 老师/运维改 `config.json` 的 api_base 指向恶意服务器 | ed25519 验签（壳内硬编码公钥）：拉到的配置无私钥必验签失败 → 拒绝 |
| 配置窥探 | 别人查看机房配置内容（服务器地址拓扑） | AES-256-GCM 加密缓存 `config.enc`（随机 nonce + GCM tag） |
| 配置伪造 | 恶意服务器下发假配置诱导降级 | 签名私钥仅管理员持有（`scripts/gen_shell_config.py --key keys/prod.key`） |
| 配置回放 | 抓包重放旧版本配置 | 缓存加密层随机 nonce；签名已覆盖内容本身 |

**语义澄清（防混淆）**：防篡改靠 **ed25519 签名**（改一个字节 → 验签失败）；加密层（AES-GCM）防本地静态窥探 + 完整性（GCM tag）。两者职责不同、互补。

### 1.3 已否决/短路的方案（决策记录）

| 方案 | 结论 |
|---|---|
| 服务端独立端点（`/api/edu/shell/config`） | **不需要**。静态托管即可服务 `GET {api_base}/shell/config.signed.json`，无 API 依赖 → 契约先行，服务端立项后再实现 |
| 纯静态明文配置 | 可被改 → 无法防篡改（本方案即其升级） |
| 公钥部署时再注入（留空 TODO） | 违背 `package.rs::SIGN_PUBKEYS` 先例（开发期预置 dev 钥、生产轮换追加）；留空会导致运行时必失败死角 → 预置 dev 公钥 |

## 2. 信任链与数据流

```
config.json（明文引导，api_base 可改——改坏最多连不上）
  └→ GET {api_base}/shell/config.signed.json      ← 静态托管即可，无需服务端端点
        └→ 壳端 ed25519 验签（key_id=shell-config-2026，公钥硬编码 SHELL_CONFIG_PUBKEYS）
              ├─ 通过 → 采信 + AES-256-GCM 加密落盘 config.enc（离线解密重验）
              └─ 失败 → 拒绝（回退离线缓存，若有）
```

**信任根**：ed25519 公钥硬编码于壳二进制（`shell_config.rs::SHELL_CONFIG_PUBKEYS`），私钥仅管理员持有。这是与内容包验签（`package.rs::SIGN_PUBKEYS`）完全对称的信任模型。

## 3. 配置包格式（信封对齐 S01 §2.2）

```json
{
  "schema_version": "1.0",
  "api_base": "https://api.loongba.education",
  "signature": {
    "alg": "ed25519",
    "key_id": "shell-config-2026",
    "nonce": "985ad4c4c2abbf08",
    "signed_payload_hash": "sha256:<canonical_json 的 sha256>",
    "sig": "<ed25519 签名 hex>"
  }
}
```

| 字段 | 说明 |
|---|---|
| `config.*` | 任意平台配置键值（未来扩展：内容包默认源、策略开关等） |
| `signature.alg` | 恒 `ed25519` |
| `signature.key_id` | 公钥表索引（支持多 key 轮换） |
| `signature.signed_payload_hash` | `sha256:` + canonical JSON（剔除 signature/checksum，sort_keys + `(",",":")` + ensure_ascii=False） |
| `signature.sig` | ed25519 签名（128 hex） |

**canonical 规则**与内容包 manifest 完全一致（共用 `package::canonical_json_sign_view`）——Python 工具与 Rust 校验互操作已验证（`python_generated_package_verifies` 测试）。

## 4. 壳端实现（Rust）

### 4.1 命令（`src-tauri/src/commands/shell_config.rs`）

| 命令 | 职责 |
|---|---|
| `shell_config_fetch` | async：GET `{api_base}/shell/config.signed.json` → 验签 → AES-GCM 加密落盘 `config.enc` → 返回签名包 |
| `shell_config_cached` | 读离线缓存：解密 → 重验签 → 返回；缓存无/解密失败/验签失败 → Err（需重新拉取） |
| `shell_config_key_status` | 当前缓存 key_id + 壳内可接受 key_id 表（前端展示/轮换提示） |

### 4.2 验签复用（`package.rs` 泛化）

```rust
// 原：verify_manifest_signature(v) —— manifest 专用
// 现：verify_signed_envelope(v, pubkeys) —— 参数化公钥表，manifest 与 shell_config 共用
pub fn verify_signed_envelope(v: &serde_json::Value, pubkeys: &[(&str, &str)]) -> Result<(), String>
```

- 校验链：signature 块存在 → alg=ed25519 → key_id 在表 → signed_payload_hash 复核 → 验签
- manifest 与壳配置从此共享同一规则，未来新增签名对象（如口令包）同法扩展

### 4.3 加密缓存（AES-256-GCM）

| 项 | 值 |
|---|---|
| 文件 | exe 同目录 `config.enc` |
| 密钥 | HKDF-SHA256 固定派生（passphrase 壳内常量，非跨机传输） |
| 布局 | `[iv:12B][ciphertext+tag]`（随机 nonce 每次写入不同密文） |
| 离线 | 解密 + 重验签后才采信（防静态篡改双保险） |

## 5. 部署与轮换

### 5.1 首次部署（开发/测试）

```powershell
# 1. 生成 dev 密钥（gitignored，自动创建）
python scripts/gen_shell_config.py --config config.dev.json --out dist/shell/config.signed.json
# 2. 脚本输出公钥 hex → 已预置在 shell_config.rs::SHELL_CONFIG_PUBKEYS（dev 公钥 431390d5...）
# 3. 将 config.signed.json 放任意静态托管，config.json api_base 指向该托管根
```

### 5.2 生产上线（换钥轮换）

```powershell
# 1. 生成生产专用密钥（独立文件，勿用 dev 钥！）
python scripts/gen_shell_config.py --config config.prod.json --key keys/prod.key --out dist/shell/config.signed.json
# 2. 把输出的公钥 hex **追加**进 SHELL_CONFIG_PUBKEYS（新条目，旧钥仍可验 = 双轨兼容）
# 3. 重新编译壳 + 发布签名包到生产托管
```

**轮换原则**：公钥表是数组——追加新 key_id 条目即可，旧配置旧钥可验、新配置新钥可验（对齐 `SIGN_PUBKEYS` 的双轨模式）。**删除旧公钥**意味着旧配置全部失效，只在主动作废时做。

### 5.3 安全操作

| 项 | 要求 |
|---|---|
| 私钥保管 | `scripts/keys/*.key` 已 gitignored；生产私钥离线保管（U 盘/密码管理器） |
| 私钥泄露 | 立即生成新 key 对、轮换公钥表、重新签发全部配置、重新编译壳 |
| 配置更新 | 只重签配置包放托管，壳端 `api_base` 不变即可感知（签名已覆盖新内容） |
